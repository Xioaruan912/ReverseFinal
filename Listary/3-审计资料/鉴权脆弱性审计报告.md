> 已替换为 `<SALT_REDACTED>` / `<REVOKED_HASH_REDACTED>`。

## 一、 执行摘要

Listary 6 的 Pro（VIP）权益判定**完全由客户端本地决定**，且判定算法为**可逆的非密码学哈希**：

```
CheckLicense(email, license):
    if license.Length != 192                        -> false
    h96 = F0(lower(email)) << 64 | F1(lower(email)) << 32 | F2(lower(email))
    code = 19 个 Base32 字符（h96 的 5bit 分组，MSB 起）
    if license[160:179] != code                     -> false
    if BLACKLIST.Contains(md5hex(lower(email) + SALT)) -> false
    return true
```

* 授权码 192 个字符中，**仅第 160–178 位（19 个字符）参与校验**，其余 173 个字符**完全不校验**；
* **没有任何签名/MAC/非对称验签**：服务端从未下发过被客户端验证的数字签名；
* 因此任何人只要知道自己的邮箱，即可**离线生成**一枚合法授权码（`patches/listary6_keygen.py`）。

实测（直接调用目标程序自身的 `LicenseChecker.CheckLicense`）：

| 输入 | 返回 |
| :--- | :--- |
| `CheckLicense("zhangsan@qq.com", keygen("zhangsan@qq.com"))` | **True** ✅ |
| `CheckLicense("zhangsan@qq.com", "A"×192)` | False ✅ |
| `CheckLicense("audit@example.com", keygen("zhangsan@qq.com"))` | False ✅（邮箱绑定生效） |
| 构造 `ProService`，写入伪造 email/key，读 `IsPro` | **True** ✅ |

> 附带发现：该产品的 **Babel 方法体防篡改确实有效**（静态 IL 补丁会被 `InvalidProgramException` 阻断），
> 但**关键业务逻辑（授权判定）却在客户端明文可逆**——加固投入与风险点严重错配。

## 三、 方法体运行时解密（绕过 Babel）

自研两件离线工装（`tools/`，源码 + 可执行文件均已归档）：

### 3.1 `NetDump.exe`
基于 .NET Framework 反射的**元数据 + IL 转储器**，可列出全程序集类型/字段/方法签名并逐条反汇编 IL，
并把非 ASCII 混淆名转义为 `\uXXXX` 便于识别。

### 3.2 `BabelDump.exe`（关键）
利用 Babel 运行时自身的解密链路还原明文 IL：

```
1. 反射定位派发器  \ue1cd::\ue00f(int, MethodBase, object, object[])
2. 取得单例静态字段 \ue1cd::\ue008
3. 调用私有解析器 \ue1cd::\ue014(id, null, null)      ← 第2/3参数必须为 null（与桩代码一致）
4. 从返回的 \ue1cb 取 Delegate → Method (RTDynamicMethod)
5. DynamicMethod.m_resolver.m_code          → 明文 IL 字节
6. DynamicMethod.m_DynamicILInfo.m_scope.m_tokens → 动态 token 表
   （token 低位为表索引，需还原 RuntimeMethodHandle / GenericFieldInfo 等包装）
7. 逐条反汇编并解析 token → 可读调用点
```

同时提供 `str <id>` 一键解出全部加密字符串常量。

**产物**：`exports/LicenseChecker.IL.txt`（明文 IL）、`dump/*.ilraw`（原始 IL 字节）。

### 4.3 等价的 C# 伪代码

```csharp
static readonly int  LicenseLen = 192;
static readonly string ALPHABET = "23456789ABCDEFGHJKLMNPQRSTUVWXYZ";
static readonly string SALT     = "<SALT_REDACTED>";
static readonly List<string> BLACKLIST = { /* 6 × 32-hex */ };

static uint F0(string s) { uint h = 0; foreach (char c in s) h = 43 * h + c; return h; }
static uint F1(string s) {                                   // ELF hash
    uint h = 0;
    foreach (char c in s) { h = (h << 4) + c; uint g = h & 0xF0000000u; if (g != 0) { h ^= g >> 24; h ^= g; } }
    return h;
}
static uint F2(string s) {
    uint h = 0;
    for (int j = 0; j < 4; j++) for (int i = j; i < s.Length; i += 4) h ^= (uint)(s[i] << ((j * 8) & 31));
    return h;
}
static string F3(string s) =>                                   // MD5 hex (lowercase)
    string.Concat(MD5.Create().ComputeHash(Encoding.UTF8.GetBytes(s)).Select(b => b.ToString("x2")));

public static bool CheckLicense(string email, string license) {
    if (email == null || license == null) return false;
    if (license.Length != 192) return false;                    // ← 唯一长度约束
    email = email.ToLowerInvariant();
    var h96 = ((BigInteger)F0(email) << 64) | ((BigInteger)F1(email) << 32) | F2(email);
    var text = "";
    for (int i = 0; i < 19; i++)
        text += ALPHABET[(int)((h96 >> (96 - (i + 1) * 5)) & 31)];
    if (license.Substring(160, 19) != text) return false;       // ← 仅校验 19/192 字符
    if (BLACKLIST.Contains(F3(email + SALT))) return false;     // ← 仅邮箱黑名单
    return true;                                                // ← 无任何签名验签
}
```

## 五、 服务端交互与设备管理（补充说明）

| 流程 | 触发点 | 端点 | 说明 |
| :--- | :--- | :--- | :--- |
| 激活 | `ProWindow → ProLicensePage → ActivateNewLicense` | `POST https://account.listary.com/api/v1/activate` | Body：`{machineId, machineName, email, licenseKey, osVersion, meta{listaryVersion}}` |
| 反激活 | `DeactivateLicense` | `api/v1/...` | 释放设备席位 |
| 自动检查 | `ScheduleAutoCheck` | 同上 | 周期性 |

> ⚠️ **服务端只做"设备席位登记/许可证有效性"业务，本地 `IsPro` 从不依赖服务端应答。**
> 即：服务端返回 400 / 网络不可达时，只要本地 `CheckLicense` 通过，`IsPro` 仍为 `True`。

**绕过入口（无需服务端）**——`Listary.Core.OptionsWindow.ProOptionsViewModel`：

```csharp
// 选项窗口 → Pro 页 → 「激活」按钮 (ey)
private bool ew() {                                   // 本地校验并落盘
    if (IsNullOrEmpty(UserName) || IsNullOrEmpty(Email) || IsNullOrEmpty(License)) return false;
    UserName = UserName.Trim();  Email = Email.Trim();
    License  = Regex.Replace(License, @"\s+", "");    // 允许粘贴时分行/带空格
    if (IsPro || LicenseChecker.CheckLicense(Email, License)) {   // ← 纯本地
        settings.Listary5LicenseName  = UserName;
        settings.Listary5LicenseEmail = Email;
        settings.Listary5LicenseKey   = License;
        IsPro = true;  return true;                   // ← 权益即刻生效
    }
    return false;
}
private void ey() { if (ew()) ev(); }                 // ev() 仅弹一个 MessageBox
```

同时 `ProOptionsViewModel::.ctor` 也直接以 `CheckLicense(...)` 决定页面显示状态。

**备用入口**（Listary 5 配置导入，`Listary.Core.Settings.Listary5.\ue0aa`）：
每次启动 `ListaryApp::Start` 会调用 `\ue0aa::\ue000()`；若 `Listary5SettingsImported == false`，
则读取 `%APPDATA%\Listary\UserData\Preferences.json`（或程序目录 `UserData\Preferences.json`），
要求 `"Version": 2`，并把 `License.Name/Email/RegCode` 映射为
`Listary5LicenseName/Email/Key` —— 一条**文件写入型绕过路径**。

### 6.6 静态补丁尝试（被防篡改阻断 —— 负面发现）

`patches/net_ilpatch.py` 可定位 `MethodDef` 并覆写其 IL 体（保持长度不变，微创）。
实测将 `LicenseChecker::CheckLicense` 覆写为 `ldc.i4.1; ret; nop…`：

```

```

文件字节级修改**完全正确**（仅 28 字节变化），但运行时报：


> 真正决定权益的是可逆算法而非二进制完整性；不改二进制、只伪造数据即可完全绕过。

## 七、 影响评估

| 维度 | 评估 |
| :--- | :--- |
| 攻击成本 | 极低。一条 Python 命令 / 任意 HTTP 客户端；无需调试器、无需绕过保护、无需服务端交互 |
| 影响范围 | 全部 Pro 特性：搜索语法/自定义过滤器/工作区/主题/自定义动作/索引增强等 |
| 持久性 | 永久（授权写入本地设置）、可离线、可重复用于任意数量邮箱 |
| 商业损失 | 直接侵蚀 Pro License 收入；黑名单机制仅能封禁已知盐值 MD5，且**新邮箱永远无法被预封禁** |
| 关联风险 | `license[0:160]` 不受任何约束 → 已泄露的真实授权码可被任意改写后继续可用；反之亦无法追溯 |
| CVSS 3.1（参考） | `AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N` ≈ **5.5 (Medium)**；若按商业影响加权则 **High** |

---

## 八、 修复建议（纵深防御）

### 8.1 最高优先级：确立服务端权威（Server-Side Authority）

1. **下线纯本地判定**。`CheckLicense` 不得作为权益唯一来源；`IsPro` 必须由服务端签发凭据推导：
   * 采用 **非对称签名许可**：服务端用私钥对 `{product, email, edition, expiry, machineId, nonce}` 签名
     （Ed25519 / ECDSA P-256 / RSA-PSS），客户端**只**内置公钥并做**真实验签**；
   * 或在启动时走 `POST /api/v1/entitlement` 拉取短期 JWT（RS256/ES256），
     本地仅缓存**带签名且带有效期**的令牌，过期即失效、离线容忍窗口有限（如 7 天）。
2. **禁止仅凭邮箱推导权益**。任何由 licensee 数据可离线重算的"校验位"都不构成鉴权
   （当前 19 字符 Base32 校验位仅相当于**拼写校验**，不是签名）。
3. 授权码格式推荐：`<base32(payload)>.<base64(signature)>`，payload 含
   `email / edition / issued_at / expire_at / key_id`，客户端验签 + 校验绑定关系。

### 8.2 传输与运行时收敛

4. **强制 TLS 证书绑定（SSL Pinning）** 并校验服务端应答签名，防止中间人伪造激活应答；
5. 服务端对激活/反激活实施**幂等性与速率限制**，并记录设备指纹异常（同一 email 大量 machineId）；
6. 关键鉴权路径下沉 native 并做**完整性自检**（与现有 Babel 防篡改结合），但**不得替代验签**。

### 8.3 授权体系治理

7. 黑名单机制由"邮箱 md5 黑名单"升级为**服务端签发撤销列表（CRL）+ 短周期令牌**，实现可撤销；
8. 引入设备席位硬上限与并发检测；异常授予自动告警；
9. 移除 `Listary5SettingsImported` 这种"一次性导入即信任"的旁路（导入数据同样需要验签）。

### 8.4 加固投入纠偏

10. 当前 Babel 防篡改**有效阻挡了二进制补丁**，却未保护**数据真实性**。
    建议将加固预算从"防补丁"转向"**防伪造**"（签名验签 + 服务端权威），
    并保留现有防篡改作为附加纵深。

## 十、 结论

1. Listary 6 Pro 的 VIP 权益**完全由客户端本地决定**，判定算法为**可逆非密码学哈希**，
   授权码 192 字符中仅 19 字符参与校验，**不存在任何签名验签** → 属典型 **CWE-602 / CWE-345**。
2. 攻击者只需自己邮箱即可**离线生成永久有效授权码**，通过产品**自带的选项 → Pro 页**完成激活，
   全程无需接触服务端、无需修改二进制。
3. 产品采用的 **Babel Obfuscator 防篡改是有效的**（静态补丁被 `InvalidProgramException` 阻断），
   但保护对象错配——**保护了二进制的完整性，却没有保护权益数据的真实性**。
4. 已通过直接调用目标程序自身逻辑完成**正向复现 + 阴性对照**，证据链完整
   （明文 IL → 算法 → 生成器 → 目标自身判定 True → `ProService.IsPro == True`）。
5. 修复方向明确：**服务端权威 + 非对称签名许可 + 可撤销短期令牌**，防篡改作为附加纵深而非替代。
