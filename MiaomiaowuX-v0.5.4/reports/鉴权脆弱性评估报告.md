# 软件安全评估与鉴权脆弱性走查报告

- **目标资产**: `miaomiaowuX-mmwx-v0.5.4-license`
- **评估类型**: 白盒代码走查 / 客户端决策逻辑安全性验证
- **缺陷分类**: `CWE-602 客户端强制服务端安全机制 + CWE-345 数据真实性验证不足 + CWE-347 签名验证逻辑缺陷（fail-open）`
- **评估时间**: 2026/09/29 周二 
- **报告归属**: `mmwx-license-audit/reports/`

---

## 1. 风险概述与脆弱性成因 (Vulnerability Summary)
妙妙屋X 是自托管的 Xray 管理与订阅拼车系统（Go 单体二进制 + 内嵌 React SPA）。许可体系采用三级 Ed25519 签名链（硬编码根公钥 -> 签名密钥证书 -> entitlement -> 会话语义绑定），但该信任链的校验只存在于浏览器端。前端在签名校验失败或 entitlement 缺失时，会 fail-open 静默回退到接口返回的未签名 plan.features。本次审计在 WSL Debian 内完成真实部署（SQLite 模式，12889 端口），通过 UPX 脱壳 + /proc/pid/mem 运行时字面量取证还原了全部许可 API 与协议，并完成 5 组受控实验：伪造 License Key、篡改 SQLite 许可缓存、离线宽限期、自建 CA + 伪造许可服务器、前端 fail-open 注入。其中 E4 证明服务端响应签名校验（pinned 公钥）有效，E5 证明前端 PRO 门禁可被未签名数据绕过，面板状态由 Invalid/TRIAL 直接变为 Valid/PRO 专业版。

## 3. 验证 PoC 与复现过程 (Proof of Concept)
PoC 脚本：poc/poc_pro_bypass.js（Playwright/Chromium 驱动真实前端）
核心逻辑（与前端 Gy() 完全同构的降级路径）：
  var verified = data['_verifiedFeatures'];              // 签名链校验结果
  var has;
  if (verified) has = verified.includes(feature);
  else          has = data?.plan?.features?.includes(feature) ?? false;   // fail-open：信任未签名数据
注入（仅改写 plan 未签名字段，无任何密钥材料）：
  v.valid = true; v.premium_theme = true;
  v.plan.name='PRO'; v.plan.display_name='专业版';
  v.plan.features=['speed_test','limiter','server_share','embedded','reality_pool'];
实测结果：
  BASELINE : license status = {Plan 试用版, features:null, valid:false} -> 面板 "Current Status: Invalid / Plan: 试用版"
  BYPASSED : license status = {Plan 专业版, features:[5 项全部], valid:true} -> 面板 "Current Status: Valid / Plan: PRO · 专业版"
  截图：reports/reports/evidence/61_baseline.png 对比 reports/reports/evidence/62_after_bypass.png
  输出：reports/poc_pro_bypass_output.txt
对照实验 E4（判定服务端防护强度）：
  自建 CA 装入系统信任库 + 在 license.miaomiaowux.com:443 部署伪造许可服务器，返回 {valid:true,...}
  主控日志："[license] response signature verification FAILED - ignoring response (possible forged license server / MITM)"
  -> 服务端 pinned 公钥验签有效，未绕过。
对照实验 E2（判定本地缓存可篡改性）：
  UPDATE system_settings SET value='{valid:true, plan:{PRO, features:[...]}}' WHERE key='license_status'
  -> 重启后主控重新判定 valid:false，plan 被覆盖为 TRIAL；但攻击者写入的 entitlement 字段被原样保留并回吐给浏览器。
其他取证要点：
  - 发行物 36,605,840 B，sha256 ecc1020a...5657 与官方 checksums.txt 及签名 manifest 一致；熵 8.0000 bit/byte，偏移 0xEC 处 UPX! 魔数，shnum=0
  - upx -d 后得到 132,604,030 B 原始 Go 二进制，pclntab 完整保留（garble 仅重命名）
  - 脱壳后 sha256 = c11d44d4aedb... 与主控上报的 build_fingerprint/client_fp.exe_sha256 完全一致，可被服务端识别
  - 内嵌 3 个 32 字节 Ed25519 公钥常量：1mOqVQuZPyeioJVLzG66z+Xdh3AdpdL0JsTmZ2nlEEA=（前端根公钥）等
  - system_settings.api_token 明文静态令牌（MM-Authorization 头），无有效期与轮换

## 4. 纵深防护与企业级加固修复建议 (Remediation)
1) 服务端权威化（首要）：把 PRO 特性判定从浏览器搬到主控（Go 侧）。将签名校验结果作为唯一 feature 来源，禁止前端在任何分支读取未签名的 plan.features。具体：删除 Gy() 中的 else 降级分支，签名校验失败一律 hasFeature=false 并显式告警，绝不 fail-open。
2) 一致性校验：主控在把 /api/user/license/status 下发给前端前，自己用内嵌 pinned 公钥完整校验一遍 entitlement 链（证书 -> entitlement -> 会话绑定），校验失败时不下发 plan/features 字段，而不是把未校验的 entitlement 原样转发。当前实现中主控只校验了许可服务器响应的签名，却把 entitlement 转发出去让浏览器决定，形成两套判据。
3) 消除明文许可缓存：system_settings.license_status 应当用 AEAD（AES-GCM 或 ChaCha20-Poly1305）加密并带 HMAC tag，密钥派生自主控 machine-id + 内嵌盐；篡改后直接判定 invalid，而不是仅忽略 valid 字段。当前实现里篡改后的 entitlement 会被原样回吐，属于不可信输入透传。
4) 客户端加固（纵深防御）：premium/glass 主题与自定义 CSS 已由服务端注入 __MMW_PREMIUM_THEME_ALLOWED__ 决定（良好实践），应把这一模式推广到全部 5 项 PRO 特性：由服务端渲染或裁剪 UI，而不是下发 features 数组让前端自行判断。
5) 反篡改链路补齐：UPX 加壳在 upx -d 面前零成本（熵 8.0、UPX! 魔数直出），应改为控制流混淆（Garble --literals --tiny 或 OLLVM）加完整性自校验；同时把 Action Guard 从 opt-in（MMWX_ACTION_GUARD=required）改为默认强制。注意 build_fingerprint/exe_sha256 已随 activate 请求上报（实测脱壳后指纹由 ecc1020a... 变为 c11d44d4...），说明服务端具备检测能力，应真正启用拒绝策略。
6) 静态全局 API Token：system_settings.api_token 明文存储 + MM-Authorization 头，无有效期与轮换，且会随备份/导出外泄。应改为可轮换、带作用域与过期时间的凭证，或直接废弃并改用会话加二次验证。
7) 传输层加固：app-secure（/api/securechan/handshake + /api/v3u 信封隧道）设计合理，但握手无客户端认证，任何可达者都能建立通道；建议对握手加速率限制与设备指纹，并明确其定位为传输加固而非访问控制，不要依赖它代替鉴权。
8) 检测与响应：许可服务器对同一 license_key 的 server_hash/机器指纹异常聚集做风控；对上报的 build_fingerprint 与官方 manifest 不一致的实例直接拒绝激活并记录，防止脱壳或改包版本继续领取授权。
9) 交付物卫生：建议许可校验敏感常量（根公钥、域分隔串、issuer）不要与业务代码同处一个前端 bundle，至少把 UI 门禁与服务端门禁解耦，避免一处 fail-open 全局失效。
